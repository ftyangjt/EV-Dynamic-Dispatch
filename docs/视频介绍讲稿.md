## 1. 开场

建议画面：展示项目 README、Streamlit 仪表盘首页，或者直接播放一段 Matplotlib 车辆轨迹动画。

讲述内容：

大家好，我们这次项目做的是一个“新能源物流车队协同调度系统”。它模拟的是城市配送场景中，平台需要不断接收新的配送任务，同时管理一批电动车辆，在车辆电量、载重、体积、货物类型、充电站排队和任务截止时间等约束下，决定哪辆车去执行哪个任务，以及什么时候去充电。

这个问题看起来像一个简单的任务分配问题，但实际上一旦加入动态任务、电动车续航和充电排队，它就变成了一个综合性的动态调度问题。我们的目标不是只写一个静态最短路 demo，而是搭建一个可以运行、可以比较策略、可以可视化观察过程的仿真实验平台。

## 2. 问题理解

建议画面：切到项目报告“项目背景与目标”或系统设计图。

讲述内容：

我们对题目的理解可以拆成四个核心对象。

第一是城市路网。城市道路被抽象成图结构，节点表示路口或地点，边表示道路。每条边不仅有距离，还包含道路类型、车道数、限速、路面质量、坡度、拥堵强度、收费和事故风险等属性。这样车辆行驶时不只是看欧氏距离，而是通过路网计算路径、时间、成本和能耗。

第二是车辆。车辆是有限资源，而且是异构的。不同车辆有不同电池容量、载重上限、体积上限、速度、能耗效率和支持的货物类型。也就是说，不是所有车都能接所有任务。

第三是任务。任务在仿真过程中动态生成，每个任务有起点、终点、重量、体积、货物类型、创建时间和截止时间。任务越早完成、路径越短、成本越低，得分越高；如果超时或无法执行，就会被记为失败。

第四是充电站。电动车调度不能忽略补能，所以系统里有多个充电站，每个站有有限数量的充电桩。车辆电量不足时需要前往充电站，并且可能排队等待。

所以这个系统本质上要解决的是：在动态变化的环境中，如何结合道路、车辆、任务和充电站状态，持续做出较合理的调度决策。

## 3. 系统总体设计

建议画面：展示项目目录结构。

讲述内容：

整个项目采用模块化设计，主要分为五个部分。

`core` 目录放核心模型，包括路网、车辆、任务、能耗、充电站和接口定义。

`algorithms` 目录放调度策略。策略层只根据当前状态生成动作，不直接修改仿真内部状态。

`simulator` 是仿真主循环，负责推进时间、生成任务、调用调度器、执行动作、更新车辆和任务状态，并统计最终指标。

`scenarios` 负责构建不同规模的城市实验场景，比如 small、medium、large 和 mega 四档城市规模。

`visualization` 负责可视化，包括 Matplotlib 动画和 Streamlit 仪表盘。

系统每个时间步的运行流程是：先推进车辆和充电站状态，再生成新任务，然后把当前任务、车辆、充电站和路网封装成 `SimulationState` 交给调度器。调度器返回 `Action`，比如分配任务 `assign_task`，或者前往充电 `go_charge`。最后由仿真器统一执行动作，并生成 `SimulationFrame` 给可视化模块使用。

这里我们特意把算法、仿真和可视化分开。这样 A 同学可以专注算法，B 同学可以维护仿真主循环，C 同学可以做展示界面，三部分通过统一接口对接。

## 4. 功能实现展示

建议画面：启动或展示 Streamlit 仪表盘。

讲述内容：

目前系统已经实现了完整的仿真闭环。

首先是动态任务生成。每个时间步都会生成若干配送任务，任务会有随机的起终点、重量、体积、货物类型和 deadline。

其次是车辆执行过程。车辆接到任务后，不是瞬间完成，而是根据路网路径计算取货和送货过程，车辆状态会从空闲变成在途，电量、载重和可用时间也会随之变化。

第三是充电过程。如果车辆电量不足，策略会生成前往充电站的动作。车辆会沿路网驶向充电站，到达后进入充电站队列，等待空闲充电桩，然后开始充电。

第四是结果统计。仿真结束后会输出完成任务数、失败任务数、完成率、准时率、平均延误、总里程、总成本、总得分、平均电量和平均充电等待时间等指标。

可视化上，我们做了两种方式。Matplotlib 动画适合快速播放一次仿真过程，可以看到车辆在路网上移动；Streamlit 仪表盘适合交互式展示，可以选择场景规模、算法策略、仿真步数、任务数量和随机种子，也可以查看任务趋势、平均电量趋势和策略对比结果。

## 5. 调度策略设计

建议画面：展示 `ev_dispatch/algorithms/strategies.py` 或仪表盘中的策略选项。

讲述内容：

我们实现了三种调度策略。

第一种是最近任务优先，也就是 `nearest`。它的思路很直观：对空闲车辆，优先选择距离当前位置最近、并且满足电量、载重、体积和货物类型约束的任务。这个策略速度快、逻辑简单，适合作为基础对照组。但它的问题是比较短视，可能忽略任务截止时间和整体收益。

第二种是最大任务优先，也就是 `largest`。它会优先处理重量较大的任务。这样做的考虑是，大重量任务更挑车辆，如果晚处理，可能只剩小车或低电车辆，导致任务失败。这个策略在重货比例较高的场景中有意义，但也可能为了大任务牺牲一些短距离任务。

第三种是综合评分策略，也就是 `composite`。它会对每个候选的“车辆-任务”组合计算一个综合得分。得分会考虑基础收益、任务优先级、deadline 紧急程度、车辆容量匹配、取货距离、送货距离、行驶时间、能耗、延误惩罚、充电站等待时间，以及完成任务后车辆是否还能到达充电站。

综合评分策略可以概括成一句话：先过滤不可行的分配，再在可行分配里选择综合收益最高的组合。相比前两种贪心策略，它考虑因素更多，在复杂场景中更稳定；代价是计算量也更大。

## 6. 数据结构与算法实现

建议画面：展示项目报告中“核心数据结构设计”部分，或切到相关代码文件。

讲述内容：

因为这是数据结构大作业，所以我们在实现时重点考虑了不同数据结构在系统中的作用。

首先是图结构。城市路网由 `RoadNetwork` 表示，底层使用图来建模道路节点和边。最短路查询基于 Dijkstra 等图算法，支持从车辆当前位置到任务起点、从任务起点到终点、以及从车辆位置到充电站的路径计算。

为了避免调度过程中反复计算相同路径，我们对最短路距离、路径、时间和道路指标做了缓存。缓存本质上是字典结构，可以把重复查询的开销降下来。

第二是字典和集合。系统中很多地方需要通过 ID 快速找到车辆、任务或充电记录。例如正在充电车辆用字典保存，已完成任务和失败任务用集合记录，避免重复统计。

第三是充电站队列。等待充电的车辆使用 `deque`，这样从队尾入队和从队头出队都是 `O(1)`。正在充电的车辆同时放在字典里，方便按车辆 ID 查询。

第四是最小堆。充电站维护了一个充电完成时间堆，堆顶就是最早充电完成的车辆。仿真推进时，只需要不断检查堆顶是否到期，不需要每个时间步扫描所有充电车辆。

第五是任务优先队列。我们实现了 `TaskPriorityPool`，底层使用 `heapq`，支持按 deadline、按重量、按优先级加 deadline 等策略组织待处理任务。它还使用懒删除机制，避免在堆中间删除元素带来的额外开销。

所以这个项目不只是用了图来寻路，还把队列、堆、字典、集合和优先队列都放到了具体业务场景里。

## 7. 实验设计与结果

建议画面：展示命令行 benchmark 输出或 `outputs/benchmarks/summary_video_script.csv`。

讲述内容：

实验部分我们使用 `benchmark.py` 运行多策略、多随机种子的对比。默认实验是在 `small_city` 场景下，对 `nearest`、`largest` 和 `composite` 三种策略分别使用 42、43、44 三个随机种子运行。

这次录制前，我们运行了一次可复现实验：

```bash
python -m ev_dispatch.benchmark --tag video_script
```

得到的平均结果大致如下：

| 策略 | 完成率 | 准时率 | 单任务成本 | 单任务里程 | 平均总分 |
| --- | ---: | ---: | ---: | ---: | ---: |
| nearest | 0.979 | 0.986 | 57.40 | 29.07 | 3521.57 |
| largest | 0.983 | 0.993 | 56.82 | 28.99 | 3598.97 |
| composite | 0.979 | 0.989 | 56.84 | 29.05 | 3585.70 |

从这个小规模实验可以观察到，三种策略的完成率都比较高，说明仿真场景和车辆配置下，系统整体能够完成大部分任务。`largest` 在这组实验里总分和完成率略高，可能是因为优先处理较重任务减少了后续不可行任务的风险。`composite` 的总分也很接近，并且单任务成本较低，说明综合评分策略在平衡成本、时间和能耗方面是有效的。`nearest` 作为简单基线表现也不错，但总分略低，说明只看取货距离并不一定能带来最优整体效果。

这里需要强调的是，这个结果不是说某个策略在所有场景下绝对最优。它更说明我们的系统已经能够通过统一指标，对不同策略进行可复现比较。后续如果切换到 medium、large 或 mega 城市场景，或者改变任务密度、车辆数量和充电站数量，策略表现可能会发生变化。

## 8. 系统特色

建议画面：展示 Streamlit 的三策略对比页面或车辆轨迹。

讲述内容：

我认为这个系统有几个比较明显的特点。

第一，它不是静态最短路问题，而是动态调度问题。任务会不断生成，车辆状态会变化，充电站也会排队。

第二，它把电动车的特点纳入了调度过程。车辆不只是有位置和载重，还有电量、能耗和补能需求。

第三，它支持多策略对比。最近优先、最大任务优先和综合评分策略都通过统一接口接入，可以在同一场景和同一随机种子下比较。

第四，它有可视化闭环。我们不仅能看到最终数字，还能通过动画观察车辆如何移动、任务如何完成、车辆什么时候去充电。

第五，它为扩展留出了接口。后续可以继续加入新的调度策略，比如滚动窗口规划、局部搜索、遗传算法，甚至强化学习策略。

## 9. 不足与思考

建议画面：回到项目报告“不足与改进方向”。

讲述内容：

当然，当前系统还有一些不足。

第一，目前路网是模拟生成的网格城市，还没有接入真实地图数据。如果要更贴近现实，可以进一步使用真实道路和实时交通速度。

第二，目前调度策略主要还是启发式和贪心式策略。它们速度快、容易解释，但不保证全局最优。后续可以加入滚动窗口规划或局部搜索，让系统在一段时间范围内一起优化多个任务。

第三，当前一个任务只由一辆车完成，没有考虑多车协同完成超大任务的情况。

第四，仿真主循环目前是按固定时间步推进。未来可以进一步升级为事件驱动系统，用事件堆统一处理任务生成、车辆到达、任务完成和充电完成，这样时间推进会更精细。

第五，能耗和充电模型还可以更真实，比如加入温度、坡度、车辆老化、电池充电曲线等因素。

这些不足也说明这个项目还有继续深入的空间。现在的版本更像一个基础实验平台，在它之上可以继续做更复杂的算法研究。

讲述内容：

总结一下，我们实现了一个面向新能源物流配送的动态调度仿真系统。系统使用图结构建模城市路网，用车辆、任务和充电站描述配送场景，通过仿真主循环持续生成任务、调用调度策略、执行任务和充电动作，并输出完成率、准时率、里程、成本、得分和电量等指标。
